# Architecture & Implementation Decisions

## Decision 1 — R2: No duplicate orders (unique constraint on `createdById` + `idempotencyKey`)

- **Decision:** the client generates one UUID per "create order" attempt and sends it as `Idempotency-Key`. The database enforces `UNIQUE (createdById, idempotencyKey)`, and the insert itself is the guard.
- On Prisma `P2002` the service loads the existing order and compares a SHA-256 hash of the canonical body: same body returns that order (200, `Idempotent-Replayed: true`), different body returns 422. The total is computed on the server.
- **Alternative:** check-then-insert (`findFirst`, then insert if nothing is found).
- **Why rejected:** it has a time-of-check/time-of-use race. Two parallel requests can both pass the check and both insert. Only the constraint is atomic.
- **Limits:** a client that sends a new key per click defeats it (the form generates the key once per attempt). Keys never expire, so the table grows. A replay returns the order as it is now, not the first response. Only this endpoint is protected.

## Decision 2 — Auth token in an httpOnly cookie, not localStorage

- **Decision:** login sets the JWT in an httpOnly, SameSite=Lax cookie (Secure in production), 2h expiry. `requireAuth` reads only that cookie and verifies it with `jwt.verify` (HS256 pinned). Roles are enforced server-side by `requireRole`, not by the React `AdminOnly` component.
- **Alternative:** return the token in the JSON body, keep it in localStorage, send it as a `Bearer` header.
- **Why rejected:** any XSS can read localStorage and exfiltrate the token. An httpOnly cookie cannot be read by JavaScript.
- **Limits:** CSRF is reduced (SameSite=Lax, JSON-only, CORS limited to `CLIENT_ORIGIN`) but not eliminated; XSS can still make authenticated requests. No revocation before expiry, and the role lives in the token until it expires. Login rate limit is per IP. Details: `Back-end/AUTH_REVIEW.md`.

## Decision 3 — PostgreSQL (local) instead of SQLite

- **Decision:** PostgreSQL 16 through Prisma 6. Single-column indexes on `status`, `createdAt` and `totalCents` serve the filter and the sorts; the unique constraint serves Decision 1. Name/email search is an unindexed substring match, which is fine at 50,000 rows. Money is stored as integer cents (`totalCents`) to avoid float rounding errors.
- **Alternative:** SQLite: one file, zero setup for the reviewer, enough for 50,000 rows.
- **Why rejected:** Postgres is closer to production (concurrent writers, real transactions, richer indexing), and the unique-constraint guarantee behind Decision 1 matters most under concurrent writes.
- **Trade-off:** the reviewer must install PostgreSQL, which puts the "under five minutes" requirement at risk. The README lists the exact setup commands, and switching to SQLite is a one-line provider change in `schema.prisma` plus a fresh migration.

## How I used AI tools

- **Project setup and commands:** an AI assistant helped with folder structure, dependency choices and the Windows/PowerShell commands.
- **Auth backend** (env validation, login/logout/me, `requireAuth`, `requireRole`, tests): generated by an AI assistant from a prompt prepared with another AI assistant, based on the legacy code in the brief. I reviewed the files, had the review document corrected where it overstated a risk (algorithm pinning is hardening, not an exploitable hole with an HS256 secret), and ran the endpoints and tests myself (Postman and the login page).
- **Login page** (form, validation, protected routes): AI-generated; I ran it against the backend and checked the error states (wrong password, empty fields, server down).
- **Orders backend** (seed, cursor-paginated list, idempotent create, tests): AI-generated from a detailed prompt; I reviewed it, checked the query plans with `EXPLAIN`, and ran the parallel duplicate-order test.
