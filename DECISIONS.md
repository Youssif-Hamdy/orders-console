# Architecture & Implementation Decisions

## Auth: Token storage — httpOnly cookie vs. localStorage

**Decision.** The login endpoint sets the JWT in an httpOnly, SameSite=Lax cookie (Secure in production) that expires after 2h. requireAuth reads the token only from that cookie and checks it with jwt.verify, with the algorithm pinned to HS256. Authorization is enforced on the server by requireRole, not by the React AdminOnly component. Passwords are stored as bcrypt hashes, and the secret comes from .env and is validated at startup.

**Alternative considered.** Return the token in the JSON body, keep it in localStorage, and send it as an Authorization: Bearer header.

**Why I rejected it.** Any XSS on the page can read localStorage and send the token to an attacker. An httpOnly cookie cannot be read by JavaScript, so the token itself cannot be stolen that way.

**Limits.** The cookie does not stop CSRF by itself. SameSite=Lax, JSON-only bodies and CORS restricted to CLIENT_ORIGIN reduce the risk, but a CSRF token would be needed for stronger protection. A page with XSS can still make authenticated requests from the user's browser. There is no revocation before expiry: logout only clears the cookie, so a copied token stays valid until it expires. The role is stored inside the token, so a demoted user keeps the old role until then. The login rate limit is per IP, which is imprecise behind a proxy.

## How I used AI tools

- Auth backend (env validation, login/logout/me, requireAuth, requireRole, tests): generated by an AI assistant from a prompt I wrote that included the legacy code. I read every file, corrected the review document where it overstated a risk (for example algorithm pinning is hardening, not an exploitable hole with an HS256 secret), and ran the endpoints and tests myself.
- Login page (form, validation, protected routes): AI-generated; I ran it against the backend and checked the error states (wrong password, empty fields, server down).
